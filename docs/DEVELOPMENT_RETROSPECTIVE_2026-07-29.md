# VRChat 实时心率桥：开发复盘与日志素材

> 这份文档不是发布说明，而是给项目开发日志准备的素材。内容按“现象、原因、
> 处理、经验”整理，可以直接拆成博客章节。时间范围覆盖首个试玩版到 v1.2.0，
> 以及 v1.2.0 之后尚未发布的持续通知和手机首页重排。

## 一句话概括

这个项目表面上只是把心率从手表传到 VRChat，实际却横跨了 Wear OS 传感器和省电策略、
手机后台服务、局域网 UDP、Windows GUI、OSC、三端多语言、安装签名和真机调试。
最难的部分不是“读到一个 BPM”，而是让这份数据在息屏、后台、网络变化和多设备之间
仍然可解释、可诊断，并且不能拿模拟数据冒充真实结果。

## 最适合写成文章主线的开发阶段

### 1. 先让链路真正跑通

最初目标是：

`Galaxy Watch → Android 手机 → Windows → VRChat OSC`

手表通过 Wear Data Layer 发消息，手机通过 UDP 发给电脑，电脑再转换为 VRChat OSC。
后来增加了电脑 ACK，形成：

`Watch → Phone → PC → Phone → Watch`

ACK 的意义不只是显示“已连接”。它能区分“手表已经交给手机”和“电脑真的收到了”，
也让每层故障都能单独定位。

### 2. 从“亮屏可用”走到“息屏还能解释”

Wear OS 的 Exercise 回调在亮屏时表现正常，但严格息屏测试出现过一个非常反直觉的结果：
接近十分钟没有实时 callback，亮屏后一次补发 591 个样本，其中 563 个来自息屏阶段。
传感器不是没测量，而是系统把回调批处理了。

这迫使项目区分两件事：

- “设备最终记录到了心率”
- “心率是否及时送到手机和电脑”

后来 1 秒实时档使用直接心率传感器和有界滚动 `PARTIAL_WAKE_LOCK`；5/10 秒档仍偏向省电。
WakeLock 不是无限持有：单次有上限、提前续期，并在停止、异常、服务销毁和 Exercise
外部结束时释放。经验是：实时性和功耗必须明确成为两个模式，不能用一个开关假装兼得。

### 3. 把诊断版和正式版分开

诊断版需要模拟心率、探针、完整字段、日志和测试工具；正式版需要低功耗和简洁界面。
早期只给手表诊断包改 applicationId 会破坏 Wear Data Layer，因为手表与手机必须匹配
applicationId 和签名。最终采用成对 flavor：

- Watch production ↔ Phone production
- Watch diagnostic ↔ Phone diagnostic

四个包可以同时安装，但两条链路各自匹配。模拟心率也带永久 `simulated=true` 标记，
电脑不会把诊断包当成真实传感器数据写入 Avatar 参数。

### 4. 扩展到小米手环和多输入

小米手环使用标准 BLE Heart Rate Service，而不是私有云接口。项目增加两条链路：

- Xiaomi Smart Band → Phone → PC
- Xiaomi Smart Band → Windows（实验）

手机 UDP 与 Windows BLE 输入必须互斥，否则两个真实 BPM 会同时驱动 OSC。设备名称、
BLE 地址等身份字段只在诊断模式里传播，普通模式只保留转发必需字段。

### 5. 从工程界面改成用户界面

三端最终统一为现代深色圆角卡片风格。这个过程证明“代码能显示”不等于 UI 完成：

- Windows 必须在 1120×820 和高 DPI 下实际截图；
- 鼠标放在曲线、输入框、下拉框或日志区域时，滚轮仍要能滚动整页；
- 手机首页必须按使用频率排序，而不是按开发模块排序；
- 英语比中文长很多，同一行左右状态很容易粘连或截断；
- 语言、版本、诊断和来源切换应该下移，当前心率、发送开关和连接状态必须在最前面。

最终手机首页顺序是：

1. 当前心率
2. 发送开关与 1/5/10 秒
3. 手表、手机、电脑连接状态
4. 电脑地址和扫码
5. 心率来源与诊断
6. 说明、语言、版本

## 开发中遇到的典型问题

### Wear OS 与传感器

| 现象 | 原因 | 处理 | 得到的经验 |
| --- | --- | --- | --- |
| 息屏后长时间没有实时心率，亮屏后突然补发几百条 | Health Services Exercise callback 被系统批处理 | 1 秒档改用直接传感器并配合有界 WakeLock；单独记录采样时间和交付时间 | “有样本”不等于“实时交付”，必须测 callback latency |
| 目标时间到了却被判测试失败 | 息屏时计时协程也被挂起，恢复后旧逻辑先超时，尾部 callback 还没执行 | 延迟结束判定，观察亮屏恢复后的尾部样本 | 生命周期恢复存在竞态，不能只看墙上时钟 |
| API 36 手表权限和旧系统不同 | 新系统使用健康数据权限，旧系统仍是 `BODY_SENSORS` 路径 | 按 API 分支请求权限并保留兼容 Manifest | 权限适配要按系统版本做真机测试，不能只靠编译 |
| Classic 表圈没有滚动或手感逐格跳 | 旋转事件只有获得焦点的组件才能收到；原始 delta 又太离散 | 显式请求焦点、消费 rotary event，并加入短时缓动 | 硬件输入适配不仅是监听事件，还要处理焦点和手感 |

### 跨设备通信

| 现象 | 原因 | 处理 | 得到的经验 |
| --- | --- | --- | --- |
| 手表还没产生心率时，手机改发送频率无法同步 | 手机尚未通过心率消息获得手表 node ID | 手机主动发现可达节点，并持久化/同步 1/5/10 秒设置 | 配置同步不能依赖业务数据先到达 |
| 约 4.99 秒到达的数据被 5 秒节流丢弃 | 定时器和系统调度有毫秒级漂移，严格按 5000 ms 判断 | 给节流边界留合理容差并增加回归测试 | 时间间隔不能假设调度器绝对精确 |
| 手动诊断请求可能被下一条心率覆盖 | 最初只有一个“最新待发包”槽位 | 心率和手动诊断分开保存，同时保持队列有界 | 低延迟不等于只保留一种消息，消息优先级必须明确 |
| 手机显示已发送，但无法确认电脑是否收到 | UDP 本身无连接语义 | 电脑返回带 sequence 的 ACK，手机验证来源和匹配关系 | “已调用 send”不能作为链路成功证据 |
| VPN 或酒店网络下电脑回执失败 | 局域网访问、网段、AP 隔离和 VPN 路由都会影响 UDP | UI 显示本机 IP、网络类型和 VPN；加入扫码配对与诊断 | 网络问题需要把地址和每一跳状态展示给用户 |

### ADB 的奇怪行为

- 手表无线 ADB 的端口会变化，旧地址可能 `offline`、超时或直接拒绝连接。
- mDNS 有时还能广播设备名和地址，但实际 TCP 端口已经关闭；“能发现”不代表“能连接”。
- 同一块手表可能同时出现 IP 和 mDNS 两个标识，命令会报 ambiguous device。
- 手机 USB ADB 比较稳定，手表无线 ADB 只应当用于安装和取证，不能当成正式数据链路。
- 正式息屏或功耗测试期间持续 Logcat、`dumpsys` 或注入输入事件会干扰结果；应先让手表
  本地记录，测试结束后再导出。
- 曾经为了测试误改过手表自动旋转，后来明确恢复并验证
  `accelerometer_rotation=0`、`user_rotation=0`。调试脚本不应留下系统设置副作用。

### Windows 与 PyInstaller

最诡异的问题之一是：同一个 one-file EXE 在正常 Windows 环境约两秒完成
`--self-test`，在受限沙箱里却表现为隐藏窗口或超时。

最终用 console 版看到 PyInstaller bootloader 只能创建空 `_MEI...` 根目录，无法在
`TEMP/TMP` 中继续解包。因为正式版是 `--windowed`，错误输出被隐藏，看起来很像业务线程
死锁。正确处理不是修改 self-test，而是：

- 在正常 Windows 进程环境构建和验证；
- 给构建脚本保留有界超时和明确的 TEMP 权限提示；
- 同时验证打包目录 EXE 和稳定安装目录 EXE；
- 不把沙箱环境的假失败当成产品缺陷。

Windows UI 也有一些 Tk 特有问题：

- 原生控件不天然符合圆角深色设计，需要统一封装按钮、输入框、下拉框和开关；
- 滚轮事件容易被曲线、表单或日志子控件截获，需要统一转发给页面滚动容器；
- 英语长文本与高 DPI 会让按钮、标签和状态挤压，必须实际启动并截图，单看代码发现不了；
- 日志不能只显示在 UI 中，最终写到
  `%LOCALAPPDATA%\VrcRealtimeHeartbeat\logs`，按日轮转、保留 14 天，并记录 Tk 回调异常堆栈。

### 手机 UI、扫码和多语言

- ZXing 的扫描线不是简单的一条静态颜色。把颜色设透明仍可能留下 Viewfinder 动画层；
  最终覆盖扫描布局并关闭 laser visibility，才真正移除横线/竖线动画。
- 扫码 Activity 默认可能跟随横屏或相机方向，最终使用自定义
  `PortraitCaptureActivity` 并锁定竖屏。
- i18n 不能只翻译字符串。英语的 `Waiting for watch report` 会和左侧设备名挤在一起，
  因此布局改为左右等宽、右侧右对齐。日语也需要单独检查换行。
- `Galaxy Watch`、`Xiaomi Smart Band`、设备名、IP、端口、BLE UUID 和 OSC 参数等
  技术标识应保持原文，避免翻译后无法对应真实设备或配置。
- 手机首页最初把语言和来源切换放在心率下面，这是“按代码模块排版”而不是“按用户频率
  排版”。真实用户反馈后才重排为心率 → 发送 → 连接状态。

### 持续通知

手机和手表后来都增加了持续状态通知，每 5 秒刷新当前 BPM 和运行状态。这里也有几个边界：

- Android 13+ 需要运行时通知权限；
- 手机前台服务使用 `connectedDevice` 类型，并保持低优先级、静音和不可清除；
- 心率超过 15 秒就显示“等待心率”，不能一直展示已经过期的 BPM；
- 手机还显示心率来源与电脑 ACK，手表显示会话状态和发送频率；
- production/diagnostic 通知 ID 可以相同，因为包名不同，二者仍能共存。

### 版本、签名和发布

- “功能正式版”不等于“商店签名正式版”。当前公开 APK 仍使用项目现有 debug 签名。
- Wear Data Layer 不只看包名，也依赖签名；来自不同机器的 Debug 签名可能导致看似安装
  成功、实际无法通信。
- 四个 APK 必须同时核对 versionName、versionCode、applicationId、证书和 SHA-256。
- GitHub Release 的附件名、README 下载表和校验文件必须一致。
- GitHub 仓库简介是写给用户的：一句话说明“它能把手表/手环心率送进 VRChat”，
  不能写成“用于测试某协议的开发仓库”。
- 发布动作必须与开发动作分开：先本地验证和报告，再经用户确认后 commit、merge、
  push、等待 CI，最后发布。

## 测试方法上的变化

项目后期不再把“编译成功”当成完成，而是分层验证：

1. 纯逻辑单元测试：协议、节流、过期、状态映射、i18n。
2. 静态门禁：Android Lint、Python `py_compile`、`git diff --check`。
3. 构建门禁：四个 Android flavor、PyInstaller EXE。
4. 安装门禁：版本、包名、签名、双包共存、通知权限。
5. 真机 UI：中文、英语、日语、顶部/底部、滚轮/触摸/表圈、扫码相机。
6. 链路闭环：Watch → Phone → PC → ACK → Phone → Watch。
7. 人工边界：物理表圈手感、真实佩戴心率、VRChat Avatar 显示和长时功耗。

其中最重要的原则是：自动化证明不了的事情必须明确写成“尚未人工验收”，不能用模拟心率、
UI 计数或一次 ACK 代替真实传感器、持续交付和 Avatar 实收。

## 可以写进日志的“奇怪瞬间”

- 手表安静了近十分钟，亮屏瞬间补发 591 个样本。
- mDNS 明明显示手表在线，连接端口却立即返回“积极拒绝”。
- EXE 在正常系统两秒自检成功，在沙箱里像死锁一样永远没有窗口。
- 扫码中央那条线从竖线变横线，最后发现它不是布局边框，而是 ZXing 自己的激光动画。
- 中文界面看起来完全正常，切成英语后两个状态在一行里黏成了一句话。
- 表圈事件代码编译通过，却因为焦点不在滚动容器上而可能完全收不到。
- 手机和手表都显示正常，但只要 flavor 包名或 Debug 签名不匹配，Wear Data Layer
  就像“什么都没发生”。
- 为了测试界面而留下的窗口、Python 预览进程、诊断服务和语言状态，也会成为下一轮测试的
  干扰，所以“清理测试现场”后来成为固定步骤。

## 仍值得在文章结尾坦诚说明的边界

- 当前 APK 还没有商店级稳定 Release 签名。
- Windows EXE 还没有商业代码签名，首次下载可能触发 SmartScreen。
- 其他 Wear OS 厂商和更多手表型号仍需逐机验证后台行为。
- VRChat Avatar 资源不在仓库中，Avatar 层需要用户自行绑定 OSC 参数。
- 长时间真实佩戴功耗应继续用固定条件记录，不能用短时电量百分比线性外推。
- v1.2.0 之后的持续通知与手机首页重排已纳入本地 `main`，尚未推送或发布。
